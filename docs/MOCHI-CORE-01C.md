# CORE-01C — Mochi 0.6.1 test candidate

October 20, 2026, America/Chicago. Scope: exact CORE-01B postfix plus independent installation identity and explicit same-owner transfer. This document describes a test-branch candidate, not installed-host or public-release acceptance.

## Installation boundary

`spindle.json` and the coupled root package version are 0.6.1. The package name and dependency/lockfile versions are unchanged. 0.7.0 is the next planned milestone only. No tag/release is created.

The new identifier is `mochi`, valid under the verified host identifier pattern. Upstream Pocket retains `lumiphone`. Mochi registers drawer `mochi-independent` and action `mochi-open-independent`; the original launcher artwork, surface mechanics, CSS-01 and Lucide contract remain. Both extension storage and userStorage are separated by host identifier. Internal `mochi/v1` paths, schemas, stable IDs and identity source discriminators remain unchanged.

**Changing the identifier changes the host installation/storage namespace. Existing lumiphone data does not appear in mochi without explicit import. There is no in-place update path claimed.** Do not ask an existing lumiphone installation to update itself to this identity-changing branch. Installation selection, permission review and disabling old automatic updates need separate operator acceptance first. No installed application was inspected or changed in this work.

## Transfer contract

Build local artifacts from this matching checkout with `bun run build:transfer-source` and `bun run build:transfer-destination`. Outputs are `tmp/transfer-source` (identifier lumiphone) and `tmp/transfer-destination` (identifier mochi), each containing a manifest and its own paired dist. These commands do not install or reload anything. The normal tracked `dist/backend.js` and `dist/frontend.js` remain the messaging package. Source and destination maintenance workers are deliberately separate from normal composition.

The source worker reads only the host-authenticated owner's own namespace. Export requires explicit consent. It inventories allowed Mochi files twice and refuses changes, unsupported files, pending/corrupt/future schemas and oversized data. Limits: 5,000 files, 32 MiB total Mochi archive bytes; optional source profile bank at most 1 MiB; UI input at most 48 MiB. Exact selected file bytes are base64 encoded with per-file SHA-256 and a versioned owner/source/manifest digest. Checksums detect integrity changes; they are not signatures or independent proof of source authenticity. The operator must retain and review the actual source export, not accept an archive whose owner and hashes were rewritten by another party.

Preflight validates fictional owners/archived accounts, legacy unassigned rooms, bindings, room/message IDs, stored order, revision histories, quotes, reactions, pins, receipts, all saved summary coverage/current pointers, preset revisions, prompts and presentation/character preferences. It checks same-owner native character/persona/image/connection references before writes. Missing required references, stale coverage, unknown files, future/damaged data, wrong owner or collisions refuse the operation; originals remain for explicit repair. Unavailable native image bytes are not downloaded or silently substituted. Browser-session-only drafts are not durable transfer records.

Global scheduler discovery and aggregate attempts are not owner data and are never copied. If the host aliases `mochi/v1/scheduler-accounts.json` into userStorage, its path/size/checksum and exclusion reason appear explicitly in the manifest; its contents and other owners are not exported. The source registry remains unchanged. Per-owner scheduler attempt history, including future timestamps after clock rollback, is preserved. Destination background opt-in is false; room scheduling and idle are disabled. Every nonterminal occurrence, including queued solicited responses and deferred drafts, is paused; claims/leases are cleared. IDs, drafts, receipts and terminal history remain. Restoring normal code, opening the UI or enabling account background messaging does not resume copied paused occurrences. Recreating/repairing a copied occurrence requires a separate reviewed owner action; no bulk resume is provided.

### Pocket-backed identities

`source:pocket` is never rewritten. Source export has a separate unchecked-by-default option to include exactly the backing persona profiles referenced by the Mochi records. The exporter reads its own source bank through scoped userStorage, filters only those selected persona entries, retains their IDs and allowed stable profile fields, records the original bank checksum, and leaves the entire source bank unchanged. It exports no unrelated character/persona profiles or RP/phone state. The selected bank is a newly serialized subset, not a claim of byte identity with the full source bank; original full-bank bytes remain in the preserved source/operator backup.

Import requires both the selected profile file and a separate explicit copy checkbox. The selected profile inventory must match the referenced identities exactly; unknown/sensitive fields, missing source profiles and extra profiles refuse. Any existing destination profile bank causes collision refusal, even if an ID matches: no silent relinking or overwriting. Repair missing/damaged backing profiles explicitly in the preserved source under a separate approved operation, then re-export and review. A clean new Mochi installation can instead start fresh. No adapter or cross-extension private-file access is introduced.

### Commit, interruption and rollback

Import requires the real owner ID typed in the maintenance UI, the reviewed archive digest, a consent checkbox and source-disabled/originals-saved attestation. Backend identity always comes from the host callback. Requests are serialized per owner; frontend request IDs include a context nonce. Logout/owner change erases review state. Maintenance teardown prevents further storage calls and suppresses late responses; a host call already sent may finish, leaving the durable recovery boundary intact.

Destination Mochi data must be empty. Existing target files/banks are never merged or overwritten. The journal retains the original export before staged writes. Each staged/committed file is hashed and a durable marker blocks normal service/scheduler storage access during incomplete transfer. File moves are individually atomic on the reviewed host; the journal makes a multi-file operation resumable. Retry the same archive with fresh reviewed consent to recover; same completed import is a no-op and does not overwrite later messages. A different transfer, damaged journal or unexpected changed target is refused.

Rollback can cover interrupted or completed imports. Review rollback first, then explicitly consent to its current destination digest. The journal retains all current selected destination bytes, including later messages, any target registry and any profile bank created by the import, before live copies are removed. Crashes resume idempotently. Original source data, original export and rollback archive remain. A changed destination after review refuses deletion. Rollback leaves a clean Mochi data scope; restoring old source code must use its matching untouched source snapshot. Do not uninstall either extension as rollback. Journal/marker damage or torn low-level filesystem writes require operator recovery from preserved exports/backups; the tool deliberately leaves normal access blocked rather than guessing. External concurrent writers, arbitrary power-loss/filesystem corruption and maliciously rewritten archives are outside the exclusive-maintenance guarantee.

## Isolated-host acceptance before changing installations

No part of this checklist has been executed against an installed host or real owner data. It requires separate approval and a disposable host, synthetic real users, synthetic fictional accounts and a fake provider only.

1. Record the host commit/version and prove authenticated extension access, owner-targeted transport, trusted auth-invalid teardown, all required scoped storage methods, permission denial behavior and exclusive stop/replacement controls. Confirm `mochi` is free; stop if another extension owns it. Do not inspect an owner's installation to answer this.
2. Back up the disposable host and source code/data with hashes. Install normal Mochi under mochi beside Pocket under lumiphone; verify distinct entries, drawer/action names and roots. A new Mochi owner must start empty; create one synthetic record and prove Pocket records remain byte-identical and invisible to Mochi. Repeat with a second real user using overlapping fictional/room IDs. Confirm only the authenticated owner's data is visible.
3. Exercise the fixed account picker/Edit/New forms at desktop and 390px/mobile: full width, scroll to Save/Cancel, Tab/Escape, save/reopen, three hide/show cycles, preserved unsent draft and one surface. Repeat without geometry/fullscreen, then on a separately approved actual Android device with keyboard/rotation. Inspect author lizardqu33n and both repo links. No model call is needed.
4. For transfer, use a separate synthetic lumiphone source containing multiple/archived fictional accounts, a legacy room, revisions, pins/reactions/quotes, summaries, presets, prompts, layout and queued/deferred jobs. Stop every normal writer. Under the approved operator administration procedure, replace only that disposable source's code with the built lumiphone source-maintenance files, preserving storage; use the host's same-identifier replacement facilities, never uninstall or copy private files between namespaces. Verify that no scheduler/provider starts.
5. Log in as the source owner, type the shown real owner ID and consent to export. For Pocket-backed identities, also choose the selected-profile option. Save the archive, per-file inventory/digest and original code/data backups. Recheck source hashes, retain it unchanged and keep it disabled/read-only. If exclusive replacement is not supported on this host, stop; no fallback private-file traversal is approved.
6. Load destination maintenance under mochi with an empty Mochi scope (and no target profile bank if copying one). Log in as the same real owner. Choose the saved archive and Review. Compare exact files, counts, hashes, exclusions, IDs, native/image references, selected profile subset and scheduler changes. Missing dependencies, wrong owner, null consent and any collision must refuse without altering live target records. Type owner ID, tick consent, separately tick profile copying if applicable, then Import. Preserve the original archive and journal.
7. Interrupt once in staging and once during copying using only this disposable host. Starting normal Mochi must stay blocked by the marker. Reload destination maintenance, review the exact same archive, give fresh consent and resume. Repeat a completed import after a new synthetic message: it must not overwrite it. Change real owner/logout while a review is pending: no prior-owner content or late response may appear. No imported job may run after restoring normal Mochi, waiting for polls or opening previews.
8. Review rollback after adding a synthetic later message and registry write. Consent to that new digest, interrupt and resume rollback. Verify every later byte is retained in the journal rollback archive, original export/source remain unchanged, selected target files are removed and an existing unrelated target profile bank is never touched. Restore matching source code only with its preserved source snapshot; keep target later-write backup separate.
9. Re-run role/permissions, owner/logout, scheduler consent/budget/dedupe and native asset tests with the fake provider. Explicitly review each paused occurrence before recreating it; no old dispatcher may run simultaneously. Provider/RP calls, real data transfer, host installation changes, beta promotion and public release remain separate approvals.
